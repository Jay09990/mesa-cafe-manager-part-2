## 2026-11-02 - CSV Formula Injection in Report Exports
**Vulnerability:** Admin export endpoints (`/api/admin/export/bookings` and `/api/admin/export/sales-log`) use `toCsv` to serialize user-supplied inputs (customer name, notes, phone, email). If user input begins with formula trigger characters (`=`, `+`, `-`, `@`, `\t`, `\r`), spreadsheet applications like Excel or LibreOffice may execute arbitrary formulas or commands when opened by café managers.
**Learning:** Quoting CSV values alone does not protect against formula execution in spreadsheet engines. Text starting with formula operators needs escaping with a leading apostrophe (`'`) while ensuring raw numeric data remains uncorrupted.
**Prevention:** Sanitize all string fields at the CSV serialization boundary (`lib/csv.ts`) by prefixing formula trigger characters with `'` if the field is a string, while preserving actual number types.

## 2026-11-03 - Timing Attack on Cron / Webhook Secret Verification
**Vulnerability:** The scheduled day-end report cron endpoint (`/api/cron/day-end-report`) verified the incoming `Authorization` header using standard equality (`!== \`Bearer \${secret}\``). Standard string equality exits early on the first non-matching byte, creating a timing side-channel (CWE-208 / CWE-385) that allows an attacker to deduce the secret character by character.
**Learning:** Checking pre-shared secrets (such as cron bearer tokens or webhook shared secrets) with naive string comparison leaks character matches via execution duration. Node's `crypto.timingSafeEqual` requires buffers of identical byte lengths, so buffer lengths must be checked before comparison.
**Prevention:** Centralize secret verification in a constant-time comparison utility (`lib/cron-auth.ts`) using `crypto.timingSafeEqual` with buffer length checking, ensuring missing or malformed tokens fail safely without throwing.
